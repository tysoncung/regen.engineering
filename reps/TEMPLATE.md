## Summary

One paragraph. What changes, in plain language. Someone should be able to read only this and know whether the rest concerns them.

## Motivation

What is wrong today. Be concrete: a knowledge tree that cannot express something, a check that cannot be automated, a term that two people read differently.

If this comes from real use, say so and describe what happened. Proposals grounded in something that actually bit someone are far more persuasive than proposals grounded in tidiness.

## Proposal

The change itself. Enough detail to implement from, including exact field names, file layouts, or wording where relevant.

## Examples

Before and after. A schema change without a worked example is very hard to evaluate.

## Impact on existing knowledge trees

State plainly whether this is additive or breaking.

- Does an existing valid tree stay valid?
- Does the validator need changes?
- Is migration needed, and can it be scripted?

A REP that breaks existing trees is not disqualified, but it must say so here rather than leaving people to discover it.

## Alternatives considered

What else was looked at, and why this option won. Include doing nothing, which is often the right answer and should have to be argued against.

## Open questions

Anything unresolved. Do not hide these; the point of the process is to have them answered before the change lands.
